# Character skill-tree dataset

This dataset contains one self-contained CSV for each lord, hero, named unique character, and legendary lord subtype in the 25 in-scope Warhammer III races.

- Game patch: 9.0 (Steam build 25507028)
- Character files: 550
- Underlying conditional node sets: 575
- Node occurrences: 28,254
- Effect rows: 140,413
- Layout: `characters/<race>/<character>.csv`

## Scope and ownership

Every included source subtype has one canonical race owner and one self-contained character file. A subtype shared by several factions or races is assigned once to its configured canonical owner; all applicable faction keys and conditional node-set variants remain inside that file.

Two scripted Tzeentch locked-army proxy subtypes are intentionally excluded because their complete tree structures exactly duplicate the normal Exalted Lords of Change. These excluded proxies do not appear as misleading renamed copies. Two distinct subtype pairs added in 9.0 share their complete source tree: Gotrek lord/hero and generic/named Handmaidens. They retain separate source identities with explicit audited exceptions; all other duplicates fail validation.

## Row model

Every character CSV uses one common long-form schema. The `record_type` column identifies character metadata, node-set variants, nodes, skill levels, effects, prerequisite links, skill locks, ancillary locks or grants, and dilemma grants. Character and applicability fields are repeated so every row can be filtered or analyzed independently.

A character subtype may have multiple node sets for faction- or campaign-specific variants. They stay together in the same character file and are distinguished by `node_set_key` and `node_set_index`.

## Machine-readable companions

- `character_index__wh3__9.0.csv`: one row per character file with counts, paths, and hashes.
- `schema_inventory__v1.csv`: ordered column definitions and data types.
- `dataset_manifest.json`: patch, totals, race coverage, and record types.
- `audit_report.json` and `audit_report.md`: generated by the validator.

## Build experiments

Filter `record_type=effect` to score skill effects by level, scope, and value. Use `prerequisite` rows to enforce path dependencies; `skill_lock` rows for mutually exclusive choices; and the node tier, indent, rank, and maximum-level fields to model legal point allocation.

## Localisation caveats

Stable game keys are canonical. The authoritative English localisation snapshot lacks names for 190 node occurrences and descriptions for 1,613 effect occurrences. Those rows remain structurally complete: keys, values, scopes, prerequisites, locks, and other source relationships are preserved. The validator reports these gaps as warnings rather than inventing labels or discarding records.

## Reproduction

From the workspace root, with `rpfm_server.exe` running locally when extraction is required:

```powershell
node .\scripts\extract-skill-source.mjs work\source_skills_9.0 9.0
node .\scripts\build-skill-trees.mjs work\source_skills_9.0 work\generated_skill_trees__final
node .\scripts\validate-skill-trees.mjs work\source_skills_9.0 work\generated_skill_trees__final
```

Install generated files only after the validator exits successfully. The validator checks source hashes, canonical ownership, file/index hashes, row types, foreign keys, node-set reconciliation, prerequisite endpoints, complete-tree uniqueness, race totals, and representative characters from all 24 races.

Shared subtypes have one canonical retrieval owner, with cross-race faction permissions preserved. Nagash access does not create duplicate character identities. The 9.0 source introduces 50 included subtypes and changes 483 of the 500 existing structural fingerprints.
